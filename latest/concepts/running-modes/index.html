    Running Modes¶

    A load-balancer rule's mode field selects its data path. This page covers the full mode enum, and why mode: 4 (fullproxy) is the prerequisite for every AI-inference feature.

    The mode enum¶

    mode is set per rule in serviceArguments. The values come from the load-balancer schema:

    mode Name Data path AI routing
    0 DNAT L4 (eBPF), default —
    1 onearm L4 (eBPF) —
    2 fullnat L4 (eBPF) —
    3 dsr L4 (eBPF) —
    4 fullproxy L7 userspace HTTP proxy Required for all AI features
    5 hostonearm L4 (eBPF) —
    6 aigw — Exists in the enum but unexercised; not covered here

    Modes 0–3 and 5 are L4 NAT modes handled on the eBPF fast path — they forward on the packet 5-tuple and never parse HTTP. They are the right choice for classic TCP/UDP/SCTP service load balancing (all inherited unchanged from upstream loxilb).

    mode: 6 (aigw)

    The enum also contains 6-aigw. It is present in the schema but is not the exercised path for the inference features documented here — no scenario in this documentation uses it. Use mode: 4 for AI routing. mode: 6 is not featured.

    Why AI features require mode: 4¶

    mode: 4 (fullproxy) is a userspace HTTP proxy. The gateway terminates the client connection, reads the full HTTP request, and can inspect and act on:

    • the requested model — the X-Model header or the body model field, for model-name routing;
    • headers — for session stickiness (e.g. mcp-session-id, a conversation header);
    • the prompt body — for KV-cache-aware prefix matching and P/D request splitting;
    • the response stream — to relay SSE with idle-timeout suppression.

    None of this is possible on the L4 modes, which make their forwarding decision from the 5-tuple before any HTTP request body exists. Every inference-aware capability — KV-cache routing, P/D disaggregation, model routing, SSE and quotas, and the MCP gateway — therefore requires mode: 4. See Architecture for how the fullproxy sits in the data plane.

    A minimal fullproxy rule (CHWBL prefix affinity over two vLLM replicas):

    curl -s -X POST http://10.10.10.254:11111/netlox/v1/config/loadbalancer \
  -H 'Content-Type: application/json' -d '{
  "serviceArguments": {
    "externalIP": "10.10.10.254", "port": 8080, "protocol": "tcp",
    "sel": 8, "mode": 4, "host": "10.10.10.254" },
  "endpoints": [
    { "endpointIP": "31.31.31.1", "targetPort": 8000, "weight": 1 },
    { "endpointIP": "32.32.32.1", "targetPort": 8000, "weight": 1 } ]}'

    loxicmd create lb 10.10.10.254 --tcp=8080:8000 --endpoints=31.31.31.1:1,32.32.32.1:1 --mode=fullproxy --select=chwbl --host=10.10.10.254

    Frontend TLS: the security enum¶

    On a fullproxy rule, security selects how the frontend connection is secured and whether the gateway re-encrypts to the backend. It is set in serviceArguments:

    security Name Frontend Backend
    0 plain Plain HTTP (default) Plain HTTP
    1 https TLS terminated at the gateway Plain HTTP to backends
    2 tls TLS TLS
    3 e2ehttps TLS terminated, then re-encrypted TLS to backends (end-to-end HTTPS)

    security: 1 terminates TLS at the gateway and proxies plain HTTP to backends; security: 3 (e2ehttps) re-encrypts so the backend connection is also TLS. Omit the field (or 0) for plain HTTP. Add TLS to any AI rule by setting security alongside mode: 4.

    Backend protocol and ALPN¶

    backend_protocol declares the HTTP capability the gateway advertises to the backend during ALPN negotiation on a fullproxy rule:

    backend_protocol Meaning
    http1 HTTP/1.1 only (default; safest)
    http2 HTTP/2 only
    both Supports both HTTP/1.1 and HTTP/2

    The default http1 is the safe choice for OpenAI-compatible vLLM and SGLang endpoints. Use http2 or both for HTTP/2 or gRPC backends (for example, some MCP transports). ALPN negotiation only applies when the backend leg is TLS (security: 2 or 3).
