    Authenticate workloads and separate key and tenant request budgets¶

    Verify HTTP identity and request limits without confusing them with packet or connection controls.

    Continue in the same lab

    Use the same root Bash session from setup. Follow the common evidence and rollback conventions throughout the exercises.

    Prerequisites and a complete authentication result¶

    Use the plain baseline rule with source controls removed. Management JWT and inference key are separate; KEY_ID is a management handle, never the inference credential. The setup key has no RPS ceiling yet. Full key field/rotation semantics remain in API key management.

    Pool share is a different resource¶

    The admission reference explains fc_tenant_max_share_pct and effective provenance. RPS limits admissions per second; share limits how one tenant occupies executing/queued units in a pool. A second key in the same tenant does not create another share. A low process accept valve precedes authentication and cannot reserve slots for a normal tenant. Do not claim normal-tenant SLA from this short tenant-RPS test. Held-stream, H2 cancellation and sustained-fairness qualification are separate experiments.

    Verify a bounded pool-share control with the public hold fixture¶

    Reuse CICD's HTTP/2 admission backend in the existing backend namespace on8088. It adds one owned host process, not another deployment. Its delay/nonce headers are fixture controls, not product API fields. The private venv adds pinned h2; it does not modify host Python. The H2 path needs an H2-capable backend: an HTTP/1-only mock produces backend503 instead of an admission verdict. Clear tenant RPS first so that an RPS429 cannot explain a pool-share rejection. A separate listener8088 uses pool capacity4/share50; two held edge-team requests occupy its2-unit share. H2 requests refuse instead of entering the H1 queue. The control tenant must still be able to execute.
